# WhiskyBase — Repository Audit

**Date:** 2026-06-11
**Scope:** Full repository read — schemas (templates + JSON), skills,
rules docs, every data YAML (15 distilleries, 20 production lines, 45
bottlings, 2 bottlers, 17 casks, 2 suppliers, 85 concepts), the three
NOTES files, and all tooling (`check_references.py`, `check_writes.py`,
`gen_data_diagrams.py`, the pre-commit hook).
**Method:** Read before judging. Validators (`check_references.py`,
`check_writes.py`) were run; `git status` was inspected. Facts are
distinguished from opinions throughout; opinions are labelled. No files
were modified.

**Reading the severity tags.** *Blocker* = breaks a stated goal or the
build; *should-fix* = real defect, no immediate breakage; *nice-to-have*
= improvement.

---

## 0. Headline findings

1. **The five Macallan files are off-schema and uncommitted.** The
   Macallan production line and all three Macallan bottlings declare a
   `schema_version` they do not conform to — they use the obsolete v0.1
   field shape. `git status` shows all five Macallan files (and the
   distillery, which *is* schema-valid) as untracked (`??`). This is
   draft work that was never migrated or committed. It is the single
   largest compliance finding (16 of the resolver's 16 schema findings).
2. **The blocking commit gate cannot catch this.** `check_writes.py`
   (the only check wired into the pre-commit hook) gates *hard
   corruption* only. Schema validation lives in `check_references.py`,
   which is warn-only by design. So off-schema data like Macallan can be
   committed without obstruction.
3. **Source-type vocabulary is specified three different ways** across
   `_common.schema.json`, `docs/source-conflict-policy.md`, and the
   templates/CLAUDE.md. The enforced list (the JSON enum) is a
   superset; the "canonical" policy doc is narrower.
4. **One genuine dead reference** (`french-oak-cask`, from
   `ardbeg-corryvreckan`) is hidden among 20 *expected* forward-refs
   (the worm-tub distillery list), because the resolver does not
   separate the two.
5. **The orientation doc (`handover.md`) is stale**: it reports 42
   bottlings (actual 45), 16 casks in §1 (actual 17), "0 findings across
   all files" (now 16), and lists tombstone files as pending deletion
   that are already gone.
6. **Build risk:** the Astro loader expects v0.2 field names
   (`produced_at_distillery`, `bottled_by`); the Macallan bottlings use
   `distillery`/`bottler`. If built, those pages would render empty
   fields or error.

The committed dataset (Harris, Bruichladdich and their ten bottlings,
plus the other 13 distilleries' worth of entries that pass schema
validation) is high quality, well-sourced, and disciplined. The
problems are concentrated in uncommitted WIP and in documentation drift,
not in the established data.

## 1. Architecture & tech stack

### The Git-as-database approach against the project's goals

The model is YAML entities + Markdown prose in a Git repo, slug
cross-references between entities, JSON Schemas as machine validators
alongside human-readable templates, a warn-only reference resolver, a
hard-corruption pre-commit gate, and a deferred Astro/Pagefind/MapLibre
build for the reader-facing site.

**Opinion: this is a good fit for the three stated goals and I do not
recommend a rewrite.** No stated goal fundamentally fails on this stack.

- *Open-source educational knowledge base.* Plain-text, diffable,
  licence-separable (CC-BY-SA data / MIT code split is already in place).
  Primary sources are cited inline. Strong fit.
- *Contributor-friendly.* PR workflow, templates with extensive inline
  guidance, a resolver a contributor can run locally. Mostly strong —
  with the friction points in §5.
- *Machine-readable.* Draft-07 JSON Schemas, a typed-ish slug graph,
  deterministic structure. Strong fit.

The single best design decision is the **peating measurement block**:
modelling PPM as `{stage, value, method, compounds, source_id}` with
source-level methodology inheritance. It correctly treats "309.1 ppm by
HPLC, standard-7, at malt spec" as a different datum from a bare "309
ppm", which is exactly the distinction the domain requires. This is
domain modelling done right.

### Weak points

**1.1 Schema enforcement is advisory, not gating. (should-fix)**
`check_references.py` runs JSON Schema validation but never exits
non-zero; the pre-commit hook runs only `check_writes.py`, which checks
for NUL bytes / truncation / YAML-parse failure — not schema conformance.
Evidence: the Macallan files violate the schema in 16 ways yet nothing
stops them being committed. *Mitigation:* add a `--strict` mode to the
resolver (or a CI step) that exits non-zero on schema findings **for
added/changed files only**, while leaving forward-reference dangling
warnings non-blocking. This preserves the deliberate "forward refs don't
block" policy (handover §8) while closing the drift gap.

**1.2 Referential integrity is one-directional and unclassified.
(should-fix, minor)** The resolver resolves outbound refs but (a) does
not separate *expected* forward refs from genuine misses, and (b) does
not verify bidirectional consistency. Evidence: `french-oak-cask` (a
real miss) sits in the same dangling bucket as 20 worm-tub forward-refs
that are expected per §8 — a contributor cannot tell them apart.
*Mitigation:* a TODO-linked allowlist of expected-pending slugs so the
resolver can report "known-pending" separately from "new dangling."

**1.3 No cross-file consistency checks. (nice-to-have)** Nothing
verifies that `distillery.production_lines` mirrors each line's
`distillery`, or that a bottling's `production_line` belongs to its
`produced_at_distillery`, or that a cask's computed `used_by` is
coherent. These invariants are currently maintained by hand.
*Mitigation:* add bidirectional assertions to the resolver.

**1.4 Query/lookup ergonomics. (nice-to-have)** The resolver does a full
`rglob` + in-memory index on every run. At ~190 files this is
instantaneous; even at thousands of files it remains trivial in Git
terms. The real ergonomic gap is that there is no queryable interface
for contributors or readers short of building the Astro site (which, per
handover, must be built Windows-side — the Linux sandbox times out and
Pagefind segfaults there). This is acceptable for the current phase but
will matter as the dataset grows. *Mitigation:* none needed now; the
build pipeline is the intended answer for readers.

**1.5 Scalability of the file-per-entity layout. (nice-to-have /
monitor)** *Fact:* the tracked Git repo is ~3 MB; the 252 MB on disk is
gitignored `node_modules`, not committed (verified: `git ls-files
site/dist` and `site/.astro` return nothing; `.gitignore` and
`site/.gitignore` both exclude `dist/`, `.astro/`, `node_modules/`).
So there is no repository-bloat problem today. The linear file-per-entity
model scales fine in Git but PR review and directory listing get
unwieldy in the thousands. Monitor; no action now.

**Verdict:** keep the stack. The weak points are all closable with
incremental tooling, not a migration.

## 2. Schema & rules compliance

### Machine validation result

`check_references.py` reports **16 JSON Schema findings, all in the
Macallan files** (185 other files validate clean). `check_writes.py`
reports no hard corruption. Full enumeration of the violations:

**`data/production_lines/macallan.yml`** — declares
`schema_version: 0.2.1` but is shaped as v0.1.

| Field present | Rule violated | Fix |
|---|---|---|
| `spirit_type`, `peated`, `peat_phenol_ppm`, `peat_origin` (top-level), `malt_supplier`, `barley_variety`, `fermentation_hours`, `spirit_strength_pct`, `target_cuts`, `cask_programme`, `distinguishing_features` | `additionalProperties: false` — none of these are in the production_line schema | Restructure to `malt:{source,maltster,variety}`, `peating:{measurements,peat_origin,notes}`, `fermentation:{...}`, `distillation:{regime,spirit_cut,new_make_abv}`, `typical_cask_program: []`; move `cask_programme`/`distinguishing_features` prose into `description` |

**`data/bottlings/macallan-sherry-oak-12.yml`**, **`macallan-double-cask-12.yml`**, **`macallan-triple-cask-15.yml`** — each declares `schema_version: 0.2` but is shaped as v0.1.

| Field present | Rule violated | Fix |
|---|---|---|
| `distillery` | unknown property; schema requires `produced_at_distillery` | rename to `produced_at_distillery` |
| `bottler` | unknown property; schema requires `bottled_by` | rename to `bottled_by: macallan` |
| (missing) | `bottler_type` is required | add `bottler_type: distillery` |
| `bottling_type: ob` | unknown property | drop (subsumed by `bottler_type`) |
| `abv_pct` | unknown property; field is `abv` | rename to `abv` |
| `age_years` | unknown property | drop (use `age_statement` as number) |
| `age_statement: '12 Year Old'` | must be number-or-null, got string | set `age_statement: 12` |
| `casks: [oloroso-sherry-butt, ...]` | unknown property; field is `maturation[].cask_type` | convert to `maturation:` list of objects |
| `production_notes`, `limited_release`, `release_year`, `bottle_volume_ml` | unknown properties | move prose to `description`; `bottle_volume_ml` → `bottle_size_ml`; `release_year` → `release_date` |

*Context (fact):* `git status` shows these five files plus
`data/distilleries/macallan.yml` as untracked. The distillery file is
schema-valid; the other four are not. This is uncommitted draft work, not
committed regression — but it is present in the working tree, and per
§1.1 nothing would block it from being committed as-is.

### Rules that are ambiguous, contradictory, or unenforceable as written

**2.1 Source-type vocabulary — contradictory across documents.**
- `schema/json/_common.schema.json` `source_type` enum (the *enforced*
  list, 12 values): `official_website, trade_publication, book,
  wikipedia, wikidata, company_filing, independent_review, interview,
  chemistry_database, regulatory_text, peer_reviewed_paper, other`.
- `docs/source-conflict-policy.md` "Source-type vocabulary" (reads as
  canonical, 7 values): omits `book, wikidata, company_filing,
  interview, other`.
- `CLAUDE.md` lists the same narrow 7.
- `schema/distillery.template.yml` and `production_line.template.yml`
  inline comments list yet a third variant (`...book | wikipedia |
  wikidata | company_filing | independent_review | interview | other`),
  omitting the chemistry/regulatory/peer-reviewed types.

A contributor reading the policy doc would believe `book` is invalid; the
validator accepts it. *Fix:* pick one canonical list (recommend the JSON
enum, since it is what's enforced) and regenerate the policy doc and
template comments from it.

**2.2 Concept "exactly one per-kind block" rule — enforcement
unverified.** `concept.template.yml` states: "Per-kind blocks. Exactly
one of these should be populated, matching the `kind` field above.
Build-time validation enforces this." I did not open
`concept.schema.json`, and the warn-only resolver does not implement a
kind↔block cross-check. *Recommendation:* confirm `concept.schema.json`
actually enforces this (e.g., via `oneOf`/conditional `required`); if it
does not, the rule is unenforced-as-written.

**2.3 `peating.unit` enum vs template.** The JSON schema allows
`unit: ppm | mg_per_litre`; the template documents only `ppm`. Minor
doc gap — widen the template comment or narrow the enum.

**2.4 Doc-precedence rule is itself ambiguous.** `handover.md` §12 says
"if the templates and this document disagree, the templates are
correct." `CLAUDE.md` calls `source-conflict-policy.md` the "full
policy" and the voice skill calls `docs/voice-register.md` "canonical."
There is no single statement of which document wins when the *templates*
and a *policy doc* disagree (as they do on source types, 2.1). *Fix:*
state a single precedence order.

## 5. User-friendliness

(Opinion-heavy section; ranked by my estimate of friction.)

### Contributor adding a new distillery, no prior context — top 5

1. **schema_version is hand-declared and unguarded.** A contributor can
   write `schema_version: 0.2` on a v0.1-shaped file (exactly what
   happened to Macallan) and get no blocking signal. The resolver warns,
   but warnings are easy to skip.
2. **Three documents disagree on valid source types (§2.1).** A
   contributor following `source-conflict-policy.md` would wrongly
   believe `book`/`interview` are invalid.
3. **Forward-reference noise.** A first resolver run shows "Dangling: 21"
   with no indication that 20 are expected. New contributors cannot tell
   their own typo from sanctioned forward-refs.
4. **The orientation doc is stale (§4.1).** New contributors are told to
   start with `handover.md`, which currently misstates counts and
   findings — eroding trust in the rest of it.
5. **Templates are excellent but verbose, and the canonical-doc
   precedence is unclear (§2.4).** Hundreds of lines of inline guidance
   are a real asset, but a newcomer hits genuine ambiguity about which
   doc wins when they conflict.

### Reader browsing the knowledge base — top 5

1. **No live data interface without the Astro build,** which per
   handover must be built Windows-side. Out of the box the data is raw
   YAML.
2. **Build risk from the Macallan WIP:** the loader (`site/src/lib/data.ts`)
   expects `produced_at_distillery`/`bottled_by`; the Macallan bottlings
   use `distillery`/`bottler`, so those pages would render blank fields
   or break the build if included.
3. **The "Islands" region** is presented without the SWA-legal-Highland
   caveat on the Harris page (Highland Park's page carries it). A reader
   could take "Islands" as a formal designation.
4. **The slug/name year mismatch (§4.2)** produces a confusing URL/identity
   for the Islay Barley 2014 release.
5. **Depth-gradient glossary (hover → educational → methodology)** is a
   genuinely strong reader feature — but, like everything reader-facing,
   it depends entirely on the unbuilt-in-sandbox pipeline, so it can't be
   validated here.

## 6. Code review (scripts/tooling)

**`scripts/check_references.py` — solid.** Clear structure, correct
slug-graph construction, sensible separation of scalar vs list refs, and
a pragmatic workaround for jsonschema's brittle cross-file `$ref`
(inlining `_common` definitions and rewriting refs at load). The
`parent`-as-cask-ref guard (only when the breadcrumb parent is
`related`) correctly avoids treating ownership `parent` company strings
as refs. No correctness bugs found. `exit 0` always is intentional and
documented. *Enhancements (not defects):* classify expected forward-refs
(§1.2); add bidirectional consistency (§1.3); add a `--strict` gating
mode (§1.1).

**`scripts/check_writes.py` — correct, one over-broad heuristic.** The
NUL-byte and YAML-parse checks are sound. The "no trailing newline =
truncation suspect" rule is a reasonable proxy but is a *blocking*
signal; it would false-positive on any legitimately newline-free text
file that gets staged. Acceptable for this text-only repo, but worth a
documented exception path if a generated artifact ever lacks a trailing
newline. Note: the default glob set excludes top-level `*.txt`, so the
`probe-*.txt` files are unscanned unless explicitly staged.

**`scripts/hooks/pre-commit` — clean.** POSIX `sh`, graceful
python3→python fallback, correct `--diff-filter=ACM` staging. Its only
limitation is scope, not correctness: it gates hard corruption only, so
schema drift is not blocked (see §1.1 — this is a design choice to
restate, not a bug in the hook).

**`scripts/gen_data_diagrams.py` — clean and appropriate.**
Deterministic SVG generation, sources cited (Miller 2024 Figs 6.7 /
8.11), data digitized into literals, writes with `newline='\n'` to avoid
CRLF. For a single-purpose generator, the absence of error handling is
fine.

**General (nice-to-have):** there are no unit tests for the scripts
themselves. Given they are the project's guard rails, a small test
fixture (a deliberately-broken YAML, a known-dangling ref) asserting the
resolver's output would be cheap insurance.
